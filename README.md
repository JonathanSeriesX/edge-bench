# edge-bench

An open, continuously-updated latency benchmark of static hosting platforms —
Vercel, Netlify, Cloudflare Pages and GitHub Pages — measured from real
probes on six continents, entirely on free tiers.

**Dashboard:** https://jonathanseriesx.github.io/edge-bench/

Everything is auditable: the raw measurements are committed to this repo as
NDJSON, the collector runs on a public GitHub Actions schedule (logs included),
and the payload lives in its own repo,
[edge-bench-payload](https://github.com/JonathanSeriesX/edge-bench-payload),
deployed byte-identically to every platform — verify the hashes yourself with
one curl loop from its README.

## Why most of these comparisons are worthless

Nearly every "Vercel vs Netlify speed test" blog post does one of these:

- **Measures the vendors' own marketing sites.** `vercel.com` and `netlify.com`
  are completely different pages with different weights, different frameworks
  and different caching. That comparison tells you nothing about the platform.
- **Runs from one location**, usually the author's laptop in a city that happens
  to sit next to one vendor's POP.
- **Runs once**, so a single cold cache or a bad BGP minute decides the winner.
- **Uses different probes for each platform**, then reports the difference
  between the probes as a difference between the platforms.

This repo is built to avoid all four.

## How it avoids them

**Identical payload.** `payload/` is a single deployable that goes to all
platforms: a byte-identical 12 KB single-page site measured at "/" (generated by `payload/build.mjs`,
so it cannot drift) plus one trivial serverless function that does nothing but
return a timestamp. The platforms serve the same bytes or the comparison is void.

**Identical probes.** [Globalping](https://globalping.io) is a free network of
probes run by the jsDelivr team. Its API lets you pass a previous measurement's
id in place of a location filter, which re-runs against *the exact same probes*.
The collector uses this: the first measurement of a round picks the probes, and
every other platform is measured against that same set, within the same few
seconds. Without it you are comparing probe assignments, not platforms.

**Percentiles over many rounds.** A round runs hourly via GitHub
Actions. The site reports p50/p75/p95/p99 across a rolling 7-day window.

**DNS reported separately.** The headline metric is TCP + TLS + server response.
DNS is broken out because a real visitor's resolver has it cached, so folding it
in mostly measures which nameserver happened to be cold when the probe ran.

## Layout

| Path | What it is |
|---|---|
| `targets.json` | Platforms, probe locations, scenarios. The only file you normally edit. |
| [`edge-bench-payload`](https://github.com/JonathanSeriesX/edge-bench-payload) | Separate repo: the identical test payload + per-platform deploy config. |
| `collector/collect.mjs` | Runs one round, appends raw NDJSON to `data/`. |
| `collector/aggregate.mjs` | Rolls raw rows into `site/data/summary.json`. |
| `site/` | Static dashboard. No build step, no dependencies. |
| `rum/` | Optional real-user layer (see below). |
| `data/` | Raw measurements, one JSON object per probe per platform per round. |

## Setup

### 1. Deploy the payload to each platform

The payload is its own repo so every platform deploys from the same source:

- **Vercel / Cloudflare Pages / Netlify** — import the payload repo in each
  dashboard ("Import from Git"). The per-platform config files at its root
  handle everything; no build settings needed.
- **GitHub Pages** — already served from the payload repo's `docs/` directory.

Then verify all platforms serve the same bytes (one-liner in the payload
repo's README). Every hash must match — if one differs, that platform is
minifying or injecting something and the comparison is not fair.

### 2. Point the config at your deployments

In `targets.json`, replace each `controlledHost` and set `"controlled": true`.
Until you do, the collector measures the vendors' marketing sites and the site
renders a banner saying the numbers are not comparable.

### 3. Run a round

```bash
node collector/collect.mjs && node collector/aggregate.mjs
```

```bash
pnpm dev
```

### 4. Automate it

Push to GitHub. `.github/workflows/collect.yml` runs a round every hour
and commits the data. Publish `site/` with GitHub Pages, or any of the five
platforms being measured.

## Rate limits

Globalping allows **250 tests/hour** unauthenticated and **500/hour** signed in,
per IP. One probe in one measurement is one test.

```
tests per round = probes x platforms x scenarios
```

The current config is 70 tests per round, run hourly. If
you add probes or platforms, either widen the cron interval or set a
`GLOBALPING_TOKEN` repo secret (free — generate one in the Globalping dashboard).
Hosting a probe yourself earns 150 extra credits/day per probe.

The collector reads `x-ratelimit-remaining` and stops the round cleanly rather
than half-filling it, so a partial round never silently skews a platform.

## The real-user layer (optional)

Datacenter probes sit on excellent transit. They tell you the floor, not what
your users get on hotel wifi. `rum/` adds the other half:

- `rum/client.js` runs in visitors' browsers, fetches the same payload from each
  platform in randomised order, and reads the phase timings out of the Resource
  Timing API.
- `rum/worker.js` is a Cloudflare Worker that stamps the country from the
  request itself and writes to Workers Analytics Engine.

Caveats that make this data messier than the synthetic side, all handled in the
client but worth knowing:

- Cross-origin timings are zeroed unless the response carries
  `Timing-Allow-Origin: *`. The payload sets it; samples that come back opaque
  anyway are dropped.
- A reused connection reports zero connect time and flatters whichever platform
  the browser already had a socket open to. Those samples are flagged and dropped.
- Measurement order biases results, so the client shuffles per visit.
- Ad blockers and privacy extensions drop some beacons, non-uniformly by region.
- It only samples a fraction of page views and waits until after `load`, so it
  does not slow down the page it lives on.

No cookies, no identifiers, no cross-site data. Geography comes from the
request, never from the client.

## What this does not measure

Latency is one axis and rarely the deciding one. Build times, DX, function
limits, pricing at scale, support and lock-in are not measured here and matter
more for most real decisions. Free tiers are measured — some platforms route
and cache differently on paid plans.
